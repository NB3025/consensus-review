# Design Notes — 규칙 뒤의 이유

SKILL.md의 규칙이 왜 그런지 궁금할 때만 읽는 참고 문서입니다. 실행 절차는 SKILL.md에 있습니다.

## Blind (리뷰어 독립성)

재현율 향상은 리뷰어들이 **서로 다른 곳에서 실패한다**는 확률적 커버리지에서 나옵니다 (`benchmark_summary.md`). 한 리뷰어가 다른 리뷰어의 결과나 이전 실행 결과를 보면 실패 지점이 겹쳐 합집합의 이득이 사라집니다. 그래서 리뷰어는 원본 문서만 읽고, 집계 결과를 리뷰어에게 "refinement"용으로 되돌리지도 않습니다.

## 파일이 정본

- 서브에이전트가 리뷰 원문을 메시지로 반환하면 플랫폼이 이를 요약·압축할 수 있습니다. 집계기가 원문 대신 요약을 받으면 인용 보존 규칙이 깨집니다. 그래서 리뷰어는 파일에 쓰고 `done`만 반환합니다.
- 리포트 본문을 채팅 텍스트와 `write` content에 두 번 내보내면 출력 토큰이 두 배가 되어 대형 리포트에서 `InvalidJson`으로 잘렸습니다 (2026-04-28 사고). 본문은 `write`에 한 번만.

## 문서는 경로로 전달

병렬 서브에이전트 호출 3개의 tool call JSON에 문서 전문이 3번 들어가면 출력 토큰 한도를 넘어 `InvalidJson`이 납니다 (2026-04-28 사고). 경로는 수십 바이트입니다. 작은 인라인 텍스트(500단어/2KB 미만)만 예외.

## 산출물은 프로젝트 디렉토리

`/tmp`는 샌드박스/컨테이너에서 서브에이전트가 접근하지 못하거나 세션 종료 시 사라질 수 있습니다. `{PROJECT_DIR}/.consensus-review-output/`는 권한 문제를 피하고, 중간 산출물을 디버깅용으로 남기며, 숨김 폴더라 탐색을 방해하지 않습니다. `.gitignore` 추가는 사용자 판단입니다. 쓰기 실패 시 다른 경로로 자동 이동하지 않는 것은 접근 문제를 사용자에게 드러내기 위해서입니다.

## Short가 기본인 이유

full 리포트(Severity·Confidence·인용·근거)는 정확하지만 길어서 실제로는 잘 읽히지 않았습니다. 대부분의 경우 필요한 것은 "무엇을 어디서 고치나"입니다. 그래서 문서 옆에는 한 줄 리포트를 두고, full 상세는 세션 디렉토리에 항상 남겨 재실행 없이 펼칠 수 있게 했습니다.

## "먼저 고칠 것"에 Severity를 함께 쓰는 이유

합의 Tier는 "찾기 쉬운가"를 재고, Severity는 "얼마나 심각한가"를 잽니다. 리뷰어가 강하고 문서가 짧으면 거의 모든 이슈를 전원이 찾습니다. 2026-10-11 스모크 테스트(`sample_aws_architecture.md`, Opus 리뷰어 3명)에서 32개 중 23개가 🔴였고 그중 10개가 MINOR였습니다. Tier만으로 나누면 short의 첫 섹션이 23줄이 되어 우선순위 신호가 사라집니다. 그래서 short의 "먼저 고칠 것"은 🔴 ∧ CRITICAL/MAJOR로 좁히고, 🔴 MINOR는 "확인할 것"으로 내립니다. full의 Tier 구분은 그대로 둡니다.

## 리뷰어 점수

Evidence Strength(1-5)는 Confidence(1-10)의 앵커(인용 개수·위치)와 같은 정보를 다시 매기는 필드라 제거했습니다. Confidence가 Tier 내 정렬 기준입니다.
